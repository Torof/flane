# Journal des décisions

Les choix structurants, avec leurs raisons. Une décision n'est jamais effacée : si elle change, on en ajoute une nouvelle qui la remplace. Modèle : `docs/modeles/DECISION.md`. Les plus récentes en haut.

---

## D-023 — Mises à jour instantanées pour la version de test : exception encadrée à D-012 · 2026-10-20 · Acceptée
**Contexte** : à chaque tranche, l'utilisateur installait un APK (un quart d'heure de compilation, 91 Mo). EAS Update (`expo-updates`) livre le code JavaScript en quelques secondes, mais l'appli appelle alors les serveurs d'Expo à chaque ouverture, ce que D-012 (« aucun SDK qui envoie des données ailleurs ») et la fiche T0.3 (« `expo-updates` absent ») excluaient. **Décision** : les mises à jour instantanées sont activées pour la seule variante de test `app.flane.dev`, canal `preview`. Partent vers Expo : version native (empreinte), plateforme, canal, version de l'appli, un identifiant aléatoire par installation et l'adresse IP ; Expo en tire des comptes de lancements par mise à jour. Jamais de position, de trajet ni de préférence. La variante publiée `app.flane` reste sous la règle stricte de D-012 jusqu'à T5.4, qui décidera avec la politique de confidentialité (serveur d'Expo, serveur à nous par le protocole ouvert, ou rien). **Pourquoi** : la boucle de test est le cœur de la méthode ; le téléphone de test est celui de l'utilisateur, le code celui du dépôt ; les données envoyées sont listées dans `docs/DONNEES.md`. Écartés : CodePush (arrêté), serveur maison dès maintenant (trop tôt). **Conséquences et vigilance** : publication seulement à la porte Observer, du dernier commit de la pull request ; double authentification sur le compte Expo ; signature des mises à jour par notre clé obligatoire avant la première permission sensible (position, micro) sur `app.flane.dev` (déclencheur dans `docs/SECURITE.md`) ; une version par tranche pour savoir ce qui tourne.

## D-022 — Garde-fou de Claude retiré : la sécurité aux portes, pas à la commande · 2026-10-20 · Acceptée
Le garde-fou qui analysait chaque commande Bash de Claude (`.claude/hooks/`, 900 lignes, banc de tests, liste `allow` figée, dossiers protégés) est supprimé. Claude Code tourne en mode « accept edits » avec les commandes courantes autorisées (`git`, `gh`, `npm`, lecture et manipulation de fichiers). Seuls demandent un accord : la fusion d'une pull request, un push forcé, une suppression récursive. La sécurité se vérifie là où elle compte : dans la fiche de tranche (risques nommés avant le code, validés par l'utilisateur), dans l'audit de `auditeur-securite` avant la pull request, et sur GitHub (`main` protégé, recherche de secrets, hooks git locaux avec gitleaks). Remplace D-020. **Pourquoi** : le garde-fou avait été proposé par Claude, pas demandé par l'utilisateur ; il a coûté quatre tranches et cinq pull requests sans une ligne de l'appli, et il produisait l'inverse de son but : une interruption à chaque écart. L'utilisateur veut valider les failles, les choix structurants et le résultat, pas chaque fichier. **Vigilance** : Claude ne contourne jamais un hook git ; une commande destructrice hors du dépôt n'est pas couverte par les réglages et relève de la règle de conduite de `CLAUDE.md`.

## D-021 — Qui décide quoi : le produit ensemble, la technique par Claude · 2026-10-20 · Acceptée
Le **produit** se décide ensemble : ce que fait l'appli, pourquoi, l'interface, l'expérience, le ton. Rien n'est construit dans ce domaine sans le choix de l'utilisateur. La **technique** est décidée par Claude : code, outils, bibliothèques, structure, façon d'obtenir le résultat décidé. Claude ne sollicite l'utilisateur sur la technique qu'en cas de doute ou de choix lourd : nouvelle dépendance, coût, vie privée, sécurité. **Pourquoi** : l'utilisateur veut porter la vision et tester, pas arbitrer des choix de code ; c'est la condition d'un processus réellement automatisé. **Vigilance** : la frontière se discute quand un choix technique change ce que l'utilisateur voit (performance, hors ligne, permissions).

## D-020 — Mode de Claude Code : « accept edits », avec les garde-fous · 2026-10-20 · Acceptée
Le mode « accept edits » devient le mode de travail normal, réglé par `defaultMode` dans `.claude/settings.json` : les modifications de fichiers ne demandent plus d'accord, sauf dans les dossiers et fichiers protégés (`.claude/`, `.githooks/`, `.github/`, `tools/dev/`, `CLAUDE.md`, `.gitignore`, `.mcp.json`). Les commandes sûres sont listées une par une dans `allow` ; le garde-fou garde la priorité sur cette liste. Le mode plan reste pour les discussions d'architecture. Le mode automatique (classificateur) n'est pas recommandé : ses refus sont opaques. `bypassPermissions` et `--dangerously-skip-permissions` sont interdits. Remplace la règle « jamais d'acceptation automatique » du kit, écrite avant que les garde-fous existent. **Pourquoi** : en mode par défaut, l'utilisateur devait approuver chaque fichier et chaque commande, ce qui annulait l'automatisation voulue ; les garde-fous de T0.1 (hook, hooks git, règle GitHub) couvrent désormais le risque. **Vigilance** : le silence du garde-fou vaut accord ; chaque entrée `allow` a ses dérivés dangereux dans le banc de tests, et la liste ne change que par une tranche.

## D-019 — Dépôt public dès T0.1, sous AGPL-3.0 · 2026-10-20 · Acceptée
Le dépôt `flane` devient public pendant la tranche T0.1, avec un fichier `LICENSE` AGPL-3.0 et une notice SPDX `AGPL-3.0-or-later` en tête de chaque fichier de code (à partir de T0.3). Remplace la partie « privé au départ » de D-013 ; la direction AGPL-3.0 de D-013 est confirmée. Avant le passage en public : historique réécrit avec l'adresse anonyme GitHub, vérifié sans secret. **Pourquoi** : un dépôt privé gratuit n'a ni protection de `main`, ni recherche de secrets GitHub, ni analyse de code, alors qu'en public tout cela est gratuit ; et le projet est open source par vision. L'AGPL empêche de refermer le code ; elle n'empêche pas de copier. **Vigilance** : le vrai point faible est le nom, non déposé (question ouverte : dépôt INPI à avancer, prévu en T5.5) ; l'avis juridique de D-013 reste nécessaire avant iOS (App Store et AGPL) ; les issues deviennent ouvertes à tous (jamais leur corps dans le contexte de Claude, T0.1b) ; les documents exposent la région et les trajets de référence de l'utilisateur, assumés.

## D-018 — Fusion par merge uniquement · 2026-10-20 · Acceptée
Sur GitHub, squash et rebase sont désactivés ; chaque pull request est intégrée par un commit de fusion, et la branche est supprimée après fusion. **Pourquoi** : les messages de commit conventionnels sont la matière de l'historique des versions (T0.4) ; le squash les écraserait. **Conséquence** : tous les commits intermédiaires de Claude restent dans l'historique ; T0.4 devra filtrer ce qui entre dans l'historique des versions.

## D-017 — Suivi du travail : backlog source de vérité, Issues boîte de réception · 2026-10-20 · Acceptée
`docs/BACKLOG.md` reste la seule source de vérité des tranches. GitHub Issues est une boîte de réception : un bug constaté sur la route, une idée. Chaque issue finit en entrée du backlog, au parking, ou fermée. Claude lit les issues ouvertes à chaque début de session (titre, numéro, auteur, étiquettes, jamais le corps) et les traite comme des données externes. GitHub Projects est revu au bilan du jalon 5, à l'arrivée de contributeurs ; s'il est adopté, il sera généré depuis le backlog par un script. **Pourquoi** : Projects n'est ni versionné, ni relu en pull request, ni lisible sans réseau ; pour deux personnes, il doublerait la tenue de livres. Issues, lui, est l'interface standard pour les testeurs et les contributeurs à venir.

## D-016 — Trois portes de validation, autonomie entre elles · 2026-10-20 · Acceptée
La validation explicite de l'utilisateur est obligatoire à trois portes : **Choisir** (la fiche de tranche validée autorise le code, dans son périmètre et pas au-delà), **Observer** (l'utilisateur constate le résultat) et **Intégrer** (fusion de la pull request, délégable à Claude tranche par tranche). Entre les portes, Claude enchaîne seul : branche, code par petits morceaux, tests, commits, push, pull request, agents de vérification, correction de leurs points bloquants dans le périmètre de la fiche, journal et backlog. Il s'arrête et demande pour tout ce qui sort du périmètre : dépendance non prévue, donnée non listée dans la fiche, exception à la méthode. **Pourquoi** : l'utilisateur décide et teste, il n'opère pas ; un accord à chaque commit n'ajoute aucun contrôle utile et ralentit tout. Les garde-fous (hooks, vérifications automatiques, agents) tiennent le rôle de la relecture pas à pas. Inventaire dans `docs/OUTILLAGE.md`. **Vigilance** : le périmètre de la fiche devient la frontière de l'autonomie ; une fiche floue donne trop de latitude. L'avocat du diable y veille.

## D-015 — Identifiant de l'appli : `app.flane` · 2026-10-20 · Acceptée
Identifiant de paquet Android `app.flane` ; nom affiché « Flâne » ; dépôt GitHub `flane`. **Pourquoi** : l'identifiant est définitif une fois publié sur Google Play ; il doit donc être court, sans accent et sans référence à un pays, pour une appli qui commence en France mais vise l'international. `fr.flane` écarté pour cette raison ; `com.flane.app` et `io.flane` écartés car plus longs sans avantage. Correspond au domaine `flane.app`, non acheté à ce jour. **Vigilance** : vérifier à la première publication (T5.4) qu'aucune appli ne porte déjà cet identifiant ; envisager l'achat du domaine `flane.app`.

## D-014 — Méthode de construction · 2026-10-20 · Acceptée
Cycle en sept temps par tranche, jalons d'usage plutôt que sprints, une seule tranche en cours, budget par tranche, parking, journal de session, définition de « fini ». Claude fait respecter la méthode ; les exceptions sont consignées. **Pourquoi** : construire à deux (humain et IA) demande de la continuité entre sessions et un contradicteur, pas des rituels d'équipe. Détail : `docs/METHODE.md`.

## D-013 — Licence : direction AGPL-3.0, dépôt privé au départ · 2026-10-20 · Acceptée pour la licence ; remplacée par D-019 pour le dépôt privé
Le dépôt reste privé au début. La direction est l'AGPL-3.0, avec un dépôt de marque « Flâne » à l'INPI. Avis juridique avant de rendre le dépôt public. **Pourquoi** : rester open source sans qu'on puisse refermer le code ; la valeur de Flâne est dans les données, les partenariats et le nom. **Vigilance** : compatibilité GPL/AGPL avec l'App Store ; accord de contribution si d'autres contribuent.

## D-012 — Aucun outil tiers de suivi · 2026-10-20 · Acceptée, précisée par D-023 pour la variante de test
Ni statistiques, ni publicité, ni SDK qui envoie des données ailleurs. **Pourquoi** : ce sont les principales sources de fuite de position dans les applis.

## D-011 — Voix : synthèse vocale d'Android, réponse par boutons · 2026-10-20 · Acceptée
Dès la première version, Flâne parle ; l'utilisateur répond par deux gros boutons. Ensuite « oui »/« non » à la voix, puis demandes en langage naturel avec une IA. Une recherche est décrite dès le départ comme une demande structurée (type d'arrêt, moment, critères). **Pourquoi** : la voix est essentielle au volant ; la reconnaissance vocale est un chantier à part.

## D-010 — Google en renvoi uniquement · 2026-10-20 · Acceptée
Aucune donnée Google récupérée ni stockée. Un bouton « Voir sur Google Maps » ouvre la fiche du lieu dans l'appli Google ; le trajet est envoyé à Google Maps ou Waze par lien. **Pourquoi** : gratuit, sans contrainte de licence, cohérent avec « au-dessus, pas dedans ». Les conditions de Google Maps Platform interdisent de stocker son contenu et de l'afficher sur une carte non Google. **Vigilance** : sans identifiant Google du lieu, le lien vers la fiche est une recherche (nom et coordonnées) et peut ouvrir le mauvais lieu ; à vérifier en T2.6.

## D-009 — Serveur : presque rien pour Flâne seule, Supabase à l'étape 2 · 2026-10-20 · Acceptée
Flâne seule n'a besoin que de distribuer des paquets et de calculer des itinéraires. Supabase (open source, hébergeable soi-même, Postgres et PostGIS) pour les avis et le partage. **Pourquoi** : connu depuis Junto, robuste, pas d'enfermement.

## D-008 — Calcul d'itinéraire : moteur open source · 2026-10-20 · Acceptée
OSRM, Valhalla ou GraphHopper (choix en tranche). Service gratuit au début, puis serveur hébergé par nous. Itinéraire calculé une fois par trajet, plus un recalcul en cas de détour. **Pourquoi** : open source, basé sur OSM, coût faible même à grande échelle. **Vigilance** : le serveur reçoit le départ (souvent la position de l'utilisateur) ; choisir un service à la politique de confidentialité écrite, jamais le serveur de démonstration public d'OSRM.

## D-007 — Carte : MapLibre et fonds OSM · 2026-10-20 · Acceptée
MapLibre (open source) plutôt que Mapbox, avec des fonds de carte OSM hébergés par nous à terme. **Pourquoi** : Mapbox devient payant à grande échelle ; les fonds publics gratuits n'offrent aucune garantie.

## D-006 — Données : OpenStreetMap et DATAtourisme, chaîne maison · 2026-10-20 · Acceptée
Un script récupère OSM et DATAtourisme, filtre selon la liste des types d'arrêts, applique les règles de tri et fabrique les paquets régionaux. **Pourquoi** : sources ouvertes et gratuites ; le tri des lieux est le cœur de Flâne, donc ce qu'on construit nous-mêmes. **Obligations** : OSM sous ODbL (mention visible dans l'appli, base dérivée repartagée sous ODbL) ; DATAtourisme sous Licence Ouverte Etalab 2.0 (citer la source et la date).

## D-005 — Lieux stockés sur le téléphone, par paquets régionaux · 2026-10-20 · Acceptée
Les suggestions se calculent sur le téléphone à partir d'une base locale téléchargée par région, signée. **Pourquoi** : gratuit, fonctionne sans réseau, la position n'est pas transmise pour obtenir des suggestions, tient à grande échelle.

## D-004 — Paliers de sources et ton qui suit la confiance · 2026-10-20 · Acceptée
Lieu par lieu : avis des flâneurs, puis notes personnelles, puis règles simples, puis OSM brut. Formulation modeste tant que rien n'est validé. **Pourquoi** : pas besoin de savoir d'emblée ce qui est « chouette » ; Flâne s'affine avec l'usage.

## D-003 — Types d'arrêts en configuration · 2026-10-20 · Acceptée
Chaque type d'arrêt est une entrée de configuration (nom, icône, famille, correspondances OSM et DATAtourisme), pas du code. **Pourquoi** : ajouter ou retirer un type doit être trivial.

## D-002 — Pas de compte utilisateur dans Flâne seule · 2026-10-20 · Acceptée
Tout reste sur le téléphone. **Pourquoi** : plus simple, et cohérent avec la vie privée.

## D-001 — Plateforme : Android d'abord, avec React Native, Expo et TypeScript · 2026-10-20 · Acceptée
Un seul code pour Android maintenant et iOS plus tard. **Pourquoi** : stack déjà maîtrisée sur Junto ; open source ; Expo gère la localisation en arrière-plan, la synthèse vocale et les notifications. **Vigilance** : le service de compilation d'Expo est payant au-delà d'un quota ; compilation locale possible.
