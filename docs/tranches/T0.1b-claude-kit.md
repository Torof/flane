## Objectif

L'utilisateur ne voit plus que les vraies portes : fusion d'une pull request, push forcé, réglage du dépôt, modification d'un garde-fou, commande indirecte ou destructrice. Tout le reste (lecture, édition des fichiers du projet, tests, commits et push sur la branche de la tranche, ouverture de pull request) se fait sans demande.

## Critère de réussite

1. Dans une session en mode « accept edits » (réglé par `defaultMode` dans `.claude/settings.json`), une tranche ordinaire ne déclenche **aucune** demande d'accord : lecture, édition dans `app/` ou `docs/`, banc de tests, `git add`, `git commit`, `git push`, `gh pr create`. Les seules demandes restantes viennent du garde-fou (fusion, push forcé, réglages, scripts externes, opérations destructrices) et des écritures dans les dossiers protégés.
2. Avec la liste `allow` active, le garde-fou garde la main : `git push --force` demande, `git commit` sur `main` est bloqué, `gh pr merge` demande. Constaté en session.
3. `tools/dev/test-hooks.sh` reste vert : la liste `allow` est exactement la liste figée du banc, et chaque préfixe autorisé a ses dérivés dangereux qui sortent « bloqué » ou « demandé » du garde-fou.

## Dedans

**D-020 — Mode de Claude Code.** « accept edits » devient le mode de travail normal : les garde-fous rendent l'acceptation automatique des modifications de fichiers raisonnable. Le mode plan reste pour les discussions d'architecture. Le mode automatique (classificateur) n'est pas recommandé : ses refus sont opaques. `bypassPermissions` et `--dangerously-skip-permissions` sont interdits. Remplace la règle « jamais d'acceptation automatique » de CLAUDE.md et de `docs/METHODE.md`.

**D-021 — Qui décide quoi.** Le produit (ce que fait l'appli, pourquoi, interface, expérience) se décide ensemble. La technique (code, outils, bibliothèques, structure) est décidée par Claude, qui ne sollicite l'utilisateur qu'en cas de doute ou de choix lourd (dépendance, coût, vie privée, sécurité).

**Liste `allow` dans `.claude/settings.json`**, figée dans le banc de tests, sans joker dangereux. Le garde-fou garde la priorité : « bloquer » ou « demander » l'emporte sur `allow`.
- Lecture du dépôt : `git status`, `log`, `diff`, `show`, `branch --show-current`, `branch -a`, `branch --list`, `rev-parse`, `ls-files`, `merge-base`, `remote -v`, `fetch`, `stash list`.
- Travail sur la branche (D-016) : `git add`, `commit`, `push`, `switch`.
- GitHub : `gh pr view`, `pr list`, `pr create`, `pr checks`, `issue list`, `run list`, `repo view`, `label list`. Pas de `gh api`, `gh pr merge`, `gh issue view` (corps d'issue : contenu externe).
- Scripts du projet : `bash tools/dev/test-hooks.sh`, `bash tools/dev/setup.sh`.
- Pas de `cat`, `find`, `grep`, `echo` : Claude a ses propres outils de lecture, soumis aux règles `deny`. `npm test`, `lint`, `typecheck` : ajoutés en T0.3.

**Garde-fou durci pour que le silence vaille accord** (objections de l'avocat du diable) :
- bloqué : `--output`/`-o` sur les sous-commandes git de lecture (écrirait n'importe où, y compris sur le garde-fou) ; `--upload-pack`/`-u` sur `fetch`, `pull`, `clone`, `ls-remote` ; `tree -o` vers un dossier protégé ;
- demandé : `checkout`/`switch` vers une branche ou un commit dont les garde-fous diffèrent (retour en arrière), `checkout -- <chemins>`, `checkout <fichier>`, `-f`/`--discard-changes` ; `branch -D/-d/-m/-M/-f` sur toute branche ; `push` vers un dépôt distant autre que `origin` ; `gc`, `prune`, `maintenance`, `reflog expire/delete`, `stash drop/clear` ; `gh pr create`/`issue create`/`comment` avec `--body-file` hors du brouillon de Claude (`/tmp/claude-*`) ; `rg --pre` ; `find -exec/-delete/-fprint` ; redirection en écriture hors du projet et du brouillon.

**Réglages** : `defaultMode: acceptEdits` ; `ask` étendu à `CLAUDE.md`, `.gitignore`, `.mcp.json` ; `.claude/settings.local.json` vidé de ses autorisations larges (restes de l'anonymisation de l'historique) et contrôlé par le banc.

**Banc de tests** : section `[kit]` (réglages valides, mode, `ask`, `allow` égale à la liste figée, aucun motif interdit, `settings.local.json` sans règle Bash, compétences et agents cités existent) ; un cas négatif par dérivé dangereux ci-dessus.

**Conventions de commande** (CLAUDE.md, `docs/CONVENTIONS.md`) : pas de `cd … &&` en tête (Claude Code évalue chaque morceau d'une commande composée, et `cd` n'est pas autorisé) ; message de commit par plusieurs `-m`, sans substitution `$(…)` ; corps de pull request par `--body-file` depuis le brouillon.

**Documentation** : D-020 et D-021 ; CLAUDE.md (modes, rôles, conventions) ; `docs/METHODE.md` (rôles, modes) ; `docs/CONVENTIONS.md` ; `docs/OUTILLAGE.md` ; `docs/SECURITE.md` (le silence du garde-fou vaut accord : corpus de dérivés dangereux) ; backlog (T0.1c).

## Risques de sécurité

| Risque | Parade |
| --- | --- |
| Une entrée `allow` ouvre un chemin que le garde-fou ne regarde pas | Liste figée, courte, sans outils de lecture génériques ; un dérivé dangereux testé par préfixe ; le garde-fou garde la priorité |
| Le garde-fou cesse de s'exécuter (fichier manquant) et `allow` passe en silence | `checkout`/`switch` vers une cible aux garde-fous différents demande ; `--output` bloqué ; `ask` sur les dossiers protégés ; la règle GitHub reste la garantie forte |
| Un fichier sensible publié dans une PR par `--body-file` | Chemin limité au brouillon de Claude, sinon demandé |
| Réglages locaux qui s'élargissent au fil des « toujours autoriser » | `settings.local.json` contrôlé par le banc |
| Mode « accept edits » : modification silencieuse de CLAUDE.md ou de `.gitignore` | `ask` sur ces fichiers |
