# T0.4c — Type-only packages do not count as an app change

**Milestone**: M0 — The workshop is ready
**Status**: Done — the owner chose this option on 2026-10-21 (« je pense que la 2 est le mieux »)
**Sheet size**: short, although it touches a check: a five-line rule the owner just chose. Devil's advocate not run; security pass kept.
**Branch**: `chore/T0.4c-types-packages`
**Budget**: half an hour

## Why

During T0.8, `version-check` went red on a `@types/node` bump: npm does not flag `@types/node` and `undici-types` as development entries, because production tools (Jest and Metro packages that Expo pulls) require them. Type declarations never reach the assembled app.

## Criterion

`version-check` ignores lockfile entries `node_modules/@types/*` and `node_modules/undici-types` (at any depth); any other production entry still counts; the T0.8 pull request (#20) turns green without a version bump.

## Out (parking)

Comparing the assembled app itself between `main` and the pull request instead of guessing from files: more exact, heavier.

## Risks

A runtime package hidden under a type-only name: `@types/*` packages hold only declarations by convention, `undici-types` is the types-only companion of `undici`. The list is explicit, not a pattern on « types » in general. An npm alias (an entry whose `name` differs from its path), a local link or an entry with an install script is never skipped. Not a security boundary (written in `docs/SECURITE.md`).

## Tests

A lockfile where only type packages change (including a nested `@types/node`) → no change; the same with `expo` changed → change. Checked on the real T0.8 lockfile: no change.

## Security pass (on commit 78d8bd5)

Conforming, nothing blocking. Two hardening points applied: aliases, links and install scripts under a type-only name are never skipped; tests pin the paths that must still count (`undici`, `undici-types-x`, code nested under a types package). 13 tests.
