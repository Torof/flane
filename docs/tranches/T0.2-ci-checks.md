# T0.2 — Vérifications automatiques (GitHub Actions)

**Jalon** : J0 — L'atelier est prêt
**Étape du cycle** : Construire
**Statut dans le backlog** : En cours
**Budget** : 1 session, avec une ligne de coupe : si le budget est atteint, l'audit des dépendances et Dependabot (partie B ci-dessous) deviennent T0.2b, avec leur propre fiche courte
**Branche** : `chore/T0.2-ci-checks`
**Validée le** : 2026-10-20 (porte Choisir ; les quatre points soumis à l'utilisateur acceptés : entrées initiales acceptées, D-025, exclusion de la famille Expo et React de Dependabot, une seule tranche avec ligne de coupe)

## Objectif

Chaque pull request est vérifiée par GitHub avant la fusion : types, lint, formatage, notices SPDX, tests, licences, secrets, dépendances. `main` refuse la fusion tant qu'une vérification obligatoire est rouge. Dependabot propose les mises à jour une fois par mois, groupées, et cesse d'échouer tous les jours sur `uuid`.

## Critère de réussite

1. Sur la pull request de la tranche, `gh pr checks` liste les jobs et ils sont verts.
2. Sur une pull request jetable (`chore/T0.2-red-check`, en brouillon, jamais fusionnée) qui contient une erreur de type volontaire, le job `app-check` est rouge et le bouton « Merge » de GitHub est grisé. L'utilisateur le constate à la porte Observer ; Claude ferme ensuite cette pull request sans la fusionner.
3. `gh api repos/Torof/flane/automated-security-fixes` répond `enabled: false` ; un contrôle Dependabot lancé à la main (« Check for updates » dans Insights → Dependency graph → Dependabot) se termine sans erreur pendant la session.
4. Un échec se lit avec `gh run view <id> --log-failed` : la première ligne du résumé nomme le job et la cause ; moins de 30 lignes utiles.

## Dedans

### Partie A — vérifications, secrets, règle sur `main`

- **Workflow `checks`** (`.github/workflows/checks.yml`), sur chaque pull request et sur chaque push de `main`, jobs :
  - `app-check` : Node de `app/.nvmrc`, `npm ci` (avec `app/.npmrc` : `ignore-scripts`, déjà le réglage local ; `tsc`, ESLint, Jest, Prettier n'ont pas besoin de script d'installation), puis `npm run check` (types, lint, formatage, SPDX, tests) et `npm run licenses`.
  - `secrets-check` : gitleaks sur tout l'historique (dépôt petit), `--redact`, sortie limitée à règle, fichier et ligne, aucun artefact déposé ; plus le refus de `.gitleaks.toml`, `.gitleaksignore` et des annotations d'exception dans les lignes ajoutées par la pull request (hors `docs/` et `*.md`), comme le hook `pre-commit`. Binaire téléchargé depuis la release GitHub, version et somme SHA-256 lues dans un nouveau `tools/dev/gitleaks.env`, seule source de vérité, lue aussi par `setup.sh` et `pre-commit` (qui dupliquent aujourd'hui la version).
- **Règle `protect-main`** complétée : `app-check` et `secrets-check` obligatoires, `strict: false` (une seule personne, une tranche à la fois : exiger la branche à jour forcerait une republication de mise à jour instantanée à chaque `docs/meta` fusionnée), `integration_id` fixé à GitHub Actions pour que seul le workflow puisse poser ces statuts. GET, modification, PUT, GET : le diff avant/après va dans le corps de la pull request.
- **Réglages du dépôt** (par `gh api`, diff dans la pull request) : approbation du propriétaire pour les workflows de tout contributeur externe ; actions limitées à celles de GitHub ; épinglage par SHA obligatoire ; jeton en lecture seule (déjà le cas, confirmé).
- **Mises à jour de sécurité automatiques désactivées** (`automated-security-fixes`) : elles échouent chaque jour sur `uuid` (le correctif existe mais la chaîne `xcode` le résout en 3.4.0 ; Dependabot refuse) et ne corrigeraient de toute façon que les dépendances directes. Les alertes restent actives et visibles.
- **Résumé court des échecs** : chaque job écrit dans `$GITHUB_STEP_SUMMARY` le job, la cause et les lignes utiles.

### Partie B — audit des dépendances, Dependabot

- **Job `deps-check`** : `npm audit --omit=dev --json` (sans `npm ci` : l'audit lit le fichier de verrouillage) lu par `tools/dev/audit.mjs` (sans dépendance, testé par `node --test`). Ne compte que les avis (entrées `via` qui sont des objets avec un identifiant GHSA), jamais les paquets vulnérables par transitivité (`expo`, `@expo/cli`…). Une alerte haute ou critique bloque, sauf si elle est acceptée dans `tools/dev/audit-accepted.json`. Modérées, basses et acceptées : listées dans le résumé, jamais bloquantes. Registre injoignable : code 2, distinct d'une faille.
  - **Critère d'acceptation** : le paquet vulnérable n'est requis par aucun module chargé à l'exécution de l'appli (bundle Metro ou code natif). Une entrée = GHSA + paquet + plage vulnérable, tous les chemins `npm explain`, la raison, la date de revue. `audit.mjs` recalcule les chemins depuis le fichier de verrouillage : s'ils diffèrent, l'entrée ne vaut plus et le job passe au rouge. Une entrée revue depuis plus de 90 jours est signalée dans le résumé et par `/debut` (pas de rouge sur une date : voir sortie de secours).
  - **Obligatoire seulement quand la pull request touche `app/package.json` ou `app/package-lock.json`** ; informatif sinon (un avis publié dans la nuit ne bloque pas une pull request de documentation). Tourne aussi chaque lundi sur `main` (`schedule`), puisque rien ne tourne entre deux pull requests.
  - **Entrées initiales**, à valider à la porte Choisir (elles sont dans l'outillage tiré par `expo`, aucune dans le code embarqué, constaté en T0.3 et revérifié ci-dessous) :

    | GHSA | Paquet | Sévérité | Chaîne | Pourquoi pas embarqué |
    | --- | --- | --- | --- | --- |
    | GHSA-vfj7-8cjw-p6xm | braces ≤ 3.0.3 | haute | micromatch → outillage (Metro, Jest, CLI) | Filtrage de fichiers côté PC |
    | GHSA-86w9-cpqp-85rv | node-forge ≤ 1.4.0 | haute | `@expo/cli`, `@expo/code-signing-certificates` | Certificats du serveur de développement et de signature, côté PC |
    | GHSA-w5hq-g745-h8pq | uuid < 11.1.1 | modérée | `xcode` → `@expo/config-plugins` → `@expo/cli` | Génération de projet iOS côté PC (non bloquante, listée pour mémoire) |
    | GHSA-hp3w-g68c-fv3c | sprintf-js ≤ 1.1.3 | modérée | `argparse` → outillage | Côté PC (non bloquante, listée pour mémoire) |

- **Dependabot** (`.github/dependabot.yml`) : GitHub Actions dans `/` et npm dans `/app`, mensuel, un groupe par écosystème (mineures et correctifs). Pour npm, la famille Expo et React est **exclue** (`expo`, `expo-*`, `@expo/*`, `react`, `react-dom`, `react-native`, `react-native-*`, `jest-expo`, `babel-preset-expo`, `eslint-config-expo`, `typescript`) : pour un 0.x comme `react-native`, Dependabot classe une rupture en « mineure », et ces paquets doivent rester alignés sur le SDK par `npx expo install --check`. Limite de deux pull requests ouvertes.
- **Traitement des pull requests Dependabot (D-025, à valider)** : une pull request Dependabot n'est jamais fusionnée telle quelle (version non montée, message de commit hors format, pas de fiche). C'est un signal : entre deux tranches, Claude ouvre une tranche `chore/Tx.y-deps-AAAA-MM` à fiche courte (diff, `npm explain`, `npx expo install --check`, empreinte native avant/après : si elle change, nouvel APK), avec la version montée et les commits au bon format, puis ferme la pull request Dependabot. Jamais pendant une autre tranche.
- **`/debut`** lit les alertes Dependabot ouvertes (`gh api repos/Torof/flane/dependabot/alerts?state=open` : paquet, sévérité, GHSA) et les entrées acceptées trop anciennes.

## Dehors

- **Contrôle « la version monte quand `app/` change »** : T0.4 (qui s'occupe des versions et des étiquettes). Les faux positifs (tests, configuration ESLint, `devDependencies`) demandent une liste précise que T0.4 écrira.
- Compilation EAS ou export Metro dans les vérifications : parking.
- Classification automatique « embarqué / outillage » par la carte des sources du bundle Metro : parking.
- Vérification du format des messages de commit dans GitHub Actions : parking, à reprendre avec T0.4.
- CodeQL : parking.
- Double authentification du compte Expo : question ouverte, inchangée.
- `Bash(eas *)` dans `.claude/settings.json` : déjà sur `main` (commit c7a29ad), rien à faire.

## Approche

- `.github/workflows/checks.yml` : `on: [pull_request, push main, schedule lundi]` ; `permissions: contents: read` ; `concurrency` par référence avec `cancel-in-progress` seulement pour les pull requests ; `runs-on: ubuntu-24.04` ; `timeout-minutes` 15 (`app-check`), 5 (`secrets-check`), 5 (`deps-check`) ; `actions/checkout` avec `fetch-depth: 0` (historique complet pour gitleaks) ; `actions/setup-node` avec `node-version-file: app/.nvmrc`, `cache: npm`, `cache-dependency-path: app/package-lock.json` ; les deux actions épinglées par SHA de commit.
- `tools/dev/gitleaks.env` : `GITLEAKS_VERSION`, `GITLEAKS_SHA256` ; `setup.sh`, `pre-commit` et le workflow le lisent.
- `tools/dev/audit.mjs` + `tools/dev/audit.test.mjs` (`node --test`, échantillon réel de sortie `npm audit` avec des `via` en chaînes), `tools/dev/audit-accepted.json`.
- `tools/dev/github-settings.sh` : applique les réglages du dépôt et la règle (GET, `jq`, PUT, GET), affiche le diff ; lancé une fois pendant la construction, après le premier run vert (GitHub n'enregistre un contexte obligatoire qu'après l'avoir vu) ; gardé dans le dépôt pour rejouer ou vérifier.
- Le hook `pre-push` ne change pas.
- Rien ne change dans `app/` : pas de version montée (`docs/CONVENTIONS.md`). Si la construction oblige à y toucher, la version passe à `0.0.3`.
- Coût : minutes gratuites (dépôt public) ; 2 à 4 minutes par run, `npm ci` environ 1 minute avec le cache. Les `docs/meta` fusionnées directement (D-024) attendent désormais ces minutes.

## Données touchées

Aucune donnée de l'appli. GitHub Actions reçoit le code du dépôt, déjà public, et télécharge les paquets npm et gitleaks. Aucun secret n'est fourni au workflow. Journaux et résumés sont publics : gitleaks en `--redact`, aucun rapport déposé. `docs/DONNEES.md` : une ligne.

## Risques de sécurité

| Risque | Parade |
| --- | --- |
| Action tierce compromise | Deux actions, de GitHub, épinglées par SHA ; le dépôt n'autorise que les actions GitHub et exige l'épinglage ; Dependabot propose les montées de SHA |
| Workflow avec trop de droits | `permissions: contents: read` ; jeton en lecture seule au niveau du dépôt ; aucun secret |
| Workflow modifié par une pull request externe | `pull_request` (jamais `pull_request_target`) ; approbation du propriétaire pour tout contributeur externe ; rien à voler |
| Entrée acceptée qui masque une vraie faille | Critère écrit (aucun module chargé à l'exécution) ; chemins recalculés à chaque run ; entrées initiales validées par l'utilisateur ; relues par `auditeur-securite` à chaque tranche ; âge signalé après 90 jours |
| Vérification rouge contournée | Pas de `bypass_actors` ; la sortie de secours est consignée dans le journal |
| gitleaks téléchargé sans contrôle, ou secret dans un journal public | Somme SHA-256 vérifiée ; `--redact` ; pas d'artefact |
| Dependabot monte un paquet de la famille Expo ou React | Famille exclue ; tranche de dépendances avec `expo install --check` et empreinte |
| Faux secret de test qui empoisonne l'historique de `main` | Aucun secret de test ; le rouge volontaire est une erreur de type sur une pull request jetable jamais fusionnée |

Renvoie à `docs/SECURITE.md` : lignes « dépendance compromise », « secret publié », « hooks contournés », « alertes `npm audit` dans l'outillage », « configuration gitleaks ».

## Plan de tests

- Cas nominal : les jobs de la pull request de la tranche sont verts ; `gh pr checks` les liste.
- Rouge volontaire : pull request jetable en brouillon avec une erreur de type ; `app-check` rouge, fusion bloquée ; constaté à Observer ; fermée ensuite.
- `audit.mjs` (`node --test`) : alerte haute non acceptée → 1 ; acceptée avec chemins identiques → 0 ; acceptée avec chemins différents → 1 ; modérée → 0 ; `via` en chaînes (paquet parent) ignoré ; entrée obsolète (paquet plus vulnérable) → avertissement ; entrée de plus de 90 jours → avertissement ; JSON invalide ou registre injoignable → 2.
- `gitleaks.env` : `setup.sh` et `pre-commit` fonctionnent toujours (commit d'essai local).
- `github-settings.sh` : diff avant/après dans le corps de la pull request ; `gh api` relu après coup.
- Dependabot : `automated-security-fixes` à `enabled: false` ; contrôle manuel réussi pendant la session ; premier rendez-vous mensuel vérifié à la session suivante.
- Test sur le téléphone : aucun (rien ne change dans l'appli).

## Prévoir sans construire

- `app-check` installe ce qu'il faut pour un futur export Metro ou une compilation EAS (parking).
- `audit-accepted.json` et ses chemins sont la base d'une classification automatique future.
- T0.4 reprendra la comparaison avec `origin/main` pour le contrôle de version et l'étiquette.

## Objections de l'avocat du diable

21 objections (5 bloquantes, 9 importantes, 7 mineures). Réponses retenues :

1. **Faux secret qui empoisonne `main` pour toujours** (merge sans réécriture, `.gitleaksignore` interdit, push protection) : retenu. Aucun secret de test ; rouge volontaire par erreur de type sur une pull request jetable jamais fusionnée.
2. **Observer impossible** (le rouge est retiré avant l'audit) : retenu. La pull request jetable reste ouverte et rouge jusqu'à Observer.
3. **Dependabot et les 0.x d'Expo** (`react-native` 0.88 → 0.89 classé « mineur ») : retenu, option (a) : famille Expo et React exclue ; alignement par `expo install --check` dans une tranche ; empreinte vérifiée.
4. **Pull requests Dependabot sans processus** (version, format de commit, tranche en cours) : retenu, D-025 : jamais fusionnées telles quelles ; reprises dans une tranche de dépendances entre deux tranches.
5. **Alertes hautes acceptées sans que l'utilisateur les voie** : retenu. Tableau des entrées initiales dans la fiche, validé à la porte Choisir.
6. **Critère embarqué / outillage contradictoire** : retenu. Critère réécrit ; chemins complets recalculés ; clé GHSA + paquet + plage. L'expiration ferme n'est pas retenue (un rouge qui tombe sur une date contredit l'objection 8) : âge signalé par le résumé et par `/debut`.
7. **`npm audit --json` compte les parents** : retenu. Seuls les avis comptent ; échantillon réel dans les tests ; code 2 pour le registre injoignable.
8. **Un avis publié la nuit bloque tout** : retenu. `deps-check` obligatoire seulement quand la pull request touche les fichiers de paquets ; sortie de secours documentée.
9. **Contrôle de version : faux positifs et mauvaise comparaison** : retenu. Déplacé en T0.4 avec les remarques (trois points, `fetch-depth`, strictement supérieure, liste précise).
10. **`strict` coûteux pour une personne** : retenu, `strict: false`.
11. **`--redact` non exigé** : retenu.
12. **`PUT` qui efface la règle** : retenu. GET, `jq`, PUT, GET, diff dans la pull request ; `integration_id` ; noms de jobs non génériques, règle sur le renommage dans `CONVENTIONS.md`.
13. **Réglages Actions au hasard** : retenu. Fixés par script : approbation pour tout contributeur externe, actions GitHub seulement, épinglage obligatoire, jeton en lecture.
14. **Personne ne lit les alertes** : retenu. `/debut` les lit ; `deps-check` tourne le lundi sur `main`.
15. **Critère flou** : retenu. Reformulé (`enabled: false`, contrôle manuel, 30 lignes).
16. **Version de gitleaks lue dans `setup.sh`** : retenu. `tools/dev/gitleaks.env` partagé ; motif d'annotation coupé dans le YAML ; portée écrite.
17. **`concurrency`, délais, image** : retenu (annulation pour les pull requests seulement ; 15/5/5 ; `ubuntu-24.04` ; chemins explicites ; `deps-check` sans `npm ci`).
18. **`npm ci` avec `ignore-scripts`** : pas de problème nouveau ; écrit dans la fiche.
19. **`Bash(eas *)` hors fiche** : déjà sur `main` depuis c7a29ad ; rien à faire.
20. **Coût** : écrit dans l'approche.
21. **Trop gros pour une session** : partiellement retenu. Le contrôle de version part en T0.4 ; la tranche reste une, avec une ligne de coupe : si le budget est atteint, la partie B devient T0.2b. L'utilisateur a choisi une seule tranche avec ligne de coupe.
