# T0.5 — Mises à jour instantanées pour la version de test, et version par tranche

**Jalon** : J0 — L'atelier est prêt
**Étape du cycle** : Observer
**Statut dans le backlog** : À tester sur la route
**Budget** : 1 session (l'empreinte native a été vérifiée avant la fiche, voir Approche)
**Branche** : `feat/T0.5-instant-updates`
**Validée le** : 2026-10-20 (porte Choisir ; D-023 acceptée par l'utilisateur en même temps)

## Objectif

À la porte Observer, l'utilisateur n'installe plus d'APK : il ouvre « Flâne (dev) » et la nouvelle tranche est là. Et il sait toujours quelle tranche tourne, parce que chaque tranche a sa version.

## Critère de réussite

1. L'utilisateur installe **un dernier APK** `preview` (version `0.0.2`). À la porte Observer, Claude publie la mise à jour du dernier commit de la pull request sur le canal `preview`. L'utilisateur ferme complètement l'appli (balayage depuis les applis récentes), la rouvre, attend quelques secondes (téléchargement en arrière-plan), la referme de la même façon, la rouvre : « À propos » passe de « Code embarqué » à « Mise à jour du <date et heure> ». Deux ouvertures, pas une : au démarrage l'appli ne bloque jamais sur le réseau.
2. « À propos » affiche la **version** (`0.0.2`), la **version native** (8 premiers caractères de l'empreinte) et l'état de la mise à jour (« Code embarqué » ou « Mise à jour du … »).
3. En mode avion, l'appli s'ouvre avec le dernier code reçu, sans attendre ni planter.
4. Une montée de version (`0.0.2` → `0.0.3`) ne change pas la version native : vérifié par un test automatique (voir Approche). Une publication pour une autre version native n'atteint jamais le téléphone : garanti par le serveur d'Expo, qui ne sert que les mises à jour de la même empreinte ; pas de critère sur l'appli pour cela.

## Dedans

- `expo-updates` (SDK 58, version exacte) et les paquets qu'il tire ; configuration : adresse du serveur de mises à jour d'Expo (`https://u.expo.dev/<identifiant de projet>`), `runtimeVersion: { policy: 'fingerprint' }` (empreinte calculée depuis les modules natifs : elle ne change que quand un module natif entre ou sort, donc elle dit exactement « il faut un nouvel APK »).
- Réglages : vérification à l'ouverture (`checkAutomatically: ON_LOAD`), `fallbackToCacheTimeout: 0` (démarrage immédiat sur le code en place, mise à jour appliquée à l'ouverture suivante), **mises à jour activées pour la seule variante `preview`** (`updates.enabled` vrai si `APP_VARIANT=preview`, faux pour `development`, qui charge depuis Metro, et pour `production`, décision reportée à T5.4).
- Canaux EAS dans `eas.json` : `channel: "preview"` sur le profil `preview` ; pas de canal pour `development` ni `production`. `cli.requireCommit: true` : impossible de publier un arbre non commité.
- Écran « À propos » : version, version native, état de la mise à jour, textes dans `fr.json`. Une fonction `updateStatus()` dans `src/ui/` lit `expo-updates` et renvoie un objet simple, testée seule (valeurs présentes, absentes, module désactivé).
- **Versionnage** : `docs/CONVENTIONS.md`, section « Versions » réécrite avec une table d'exemples ; `package.json` est la seule source (`app.config.ts` la lit déjà) ; T0.5 passe l'appli en `0.0.2`. Le modèle de fiche et `docs/METHODE.md` reçoivent la ligne « version montée » dans la définition de « fini », et la porte Observer décrite par la mise à jour instantanée (APK seulement si la version native change).
- **Décision D-023** (à valider à la porte Choisir, voir Risques) : exception à D-012 pour la variante de test, données listées, retour à la règle stricte pour `app.flane`.
- Procédure de publication, dans `CONVENTIONS.md` et le README : depuis un arbre propre au dernier commit de la PR, `APP_VARIANT=preview EXPO_NO_TELEMETRY=1 eas update --channel preview --platform android --message "T0.x <hash court>" --non-interactive`. Republier après chaque correction de l'audit ou de la relecture. Si une PR est refusée : `eas update:republish` du dernier état de `main`. Publier seulement à la porte Observer.
- Tests : `updateStatus()` ; `app.config.ts` : `updates.enabled` vrai pour `preview` seulement ; **empreinte stable** : la configuration Expo résolue pour `development` et pour `preview` est identique sur les champs qui entrent dans l'empreinte, **sauf `updates.enabled` et la permission `ACCESS_NETWORK_STATE` bloquée** (constaté à la construction : `updates` entre dans l'empreinte, donc le client de développement et l'APK d'essai ont deux versions natives différentes, ce qui est sans conséquence puisque seul l'APK d'essai reçoit des mises à jour ; la publication se fait toujours avec `APP_VARIANT=preview`). Le test compare la configuration résolue entière, moins `version` ; la version n'entre pas dans l'empreinte (test qui résout la config avec deux versions).
- `docs/DONNEES.md` : nouvelle ligne pour la variante de test. `docs/SECURITE.md` : risque « code livré hors du magasin », parade, et **déclencheur** : signature des mises à jour par notre clé obligatoire avant la première tranche qui donne une permission sensible (position, micro) à `app.flane.dev`. Glossaire : mise à jour instantanée, version native, canal.
- Un APK `preview` et un client de développement compilés (l'empreinte change : `expo-updates` est un module natif), empreinte du build comparée à l'empreinte locale (`eas fingerprint:compare`), manifeste relu (`tools/dev/read-manifest.py`). `expo-updates` déclare `ACCESS_NETWORK_STATE` (relevé par l'audit dans son manifeste), qu'il n'utilise qu'en mode « Wi-Fi seulement » : bloquée pour `preview` et `production`, gardée pour le client de développement (Metro). Attendu dans l'APK `preview` : `INTERNET` seule, `allowBackup=false`, aucun composant exporté nouveau, `expo-channel-name: preview`.

## Dehors

- Mises à jour instantanées pour la version publiée `app.flane` : **T5.4**, avec la politique de confidentialité (T5.2). Choix à ce moment-là : serveur d'Expo, serveur à nous (protocole ouvert), ou pas de mises à jour.
- Historique des versions automatique, étiquettes Git `v0.x.y` : **T0.4**.
- Vérifications automatiques : **T0.2** (suivante).
- Mise à jour « à chaud » sans redémarrage (bouton « redémarrer ») : parking.
- Signature des mises à jour par notre clé : pas maintenant, mais **déclencheur écrit** (voir Dedans), pas T5.4.
- Retour en arrière automatique quand une mise à jour plante au démarrage : fourni par `expo-updates` ; constaté dans la fiche seulement.

## Approche

- **Vérifié avant la fiche** (`@expo/fingerprint` 0.21.5, préréglage par défaut, Android) : l'empreinte est identique pour `development` et `preview` (`d2d3412e…`) et différente pour `production` (`2bf4dc96…`, à cause du nom et de l'identifiant, ce qui est voulu) ; **passer `version` de `0.0.1` à `0.0.2` ne la change pas** (le champ `version` n'entre pas dans l'empreinte, seuls `android`, `extra`, `icon`, `name`, `orientation`, `platforms`, `plugins`, `scheme`, `sdkVersion`, `slug`, `userInterfaceStyle` y entraient avant la tranche ; `runtimeVersion` et `updates` s'y ajoutent avec elle). Les objections 1 et 2 de l'avocat sont donc levées par les faits ; le test « empreinte stable » empêche une régression.
- `npx expo install expo-updates`, puis relecture de ce qu'`eas update:configure` propose (il ne sait pas écrire dans `app.config.ts` : report à la main). `app.config.ts` : `runtimeVersion`, `updates: { url, enabled: variant === 'preview', checkAutomatically: 'ON_LOAD', fallbackToCacheTimeout: 0 }`.
- `src/ui/updateStatus.ts` + test ; `AboutScreen` l'affiche. `package.json` → `0.0.2`.
- Ordre : code et tests → APK compilés (les deux profils) → comparaison d'empreinte → audit et relecture → corrections → PR → **porte Observer** : l'utilisateur installe l'APK `preview`, puis Claude publie la mise à jour du dernier commit et l'utilisateur constate le critère 1. Le code publié est celui de la PR, audité.

## Données touchées

Nouveau, pour la variante `preview` (`app.flane.dev`) seulement : à chaque ouverture, l'appli appelle le serveur de mises à jour d'Expo. Partent (relevé par l'audit dans le code natif d'`expo-updates`), à chaque ouverture, vers les serveurs d'Expo (manifeste sur `u.expo.dev`, ressources sur leur CDN ; l'adresse IP est vue aux deux endroits) : plateforme, versions du protocole, version native (empreinte), canal, un identifiant aléatoire propre à l'installation (`EAS-Client-ID`), l'identifiant de la mise à jour en cours et de celle embarquée, la liste des mises à jour récemment en échec, et le texte d'une éventuelle erreur fatale d'`expo-updates` au lancement précédent (1024 caractères au plus, interne au module). Expo en tire des comptes de lancements et des taux d'échec par mise à jour. Jamais de position, de trajet ni de préférence ; la version de l'appli ne figure pas dans la requête. Reviennent : le code JavaScript et les ressources de l'appli. Sur le téléphone, dans l'espace privé : identifiant d'installation, base des mises à jour, fichiers, journaux (24 h). Ligne de `docs/DONNEES.md`, marquée « variante de test ; version publiée : décision en T5.4 ». Le client de développement ne va pas chercher de mise à jour tout seul (chargement manuel possible depuis son lanceur) ; la variante `production` n'appelle pas ce serveur.

## Risques de sécurité

| Risque | Parade |
| --- | --- |
| **Écart de principe** : D-012 (« aucun SDK qui envoie des données ailleurs ») et la fiche T0.3 (« `expo-updates` absent » comme parade au suivi caché) | **D-023**, validée explicitement par l'utilisateur : exception limitée à `app.flane.dev` canal `preview`, données listées ci-dessus, statistiques d'Expo nommées, règle stricte inchangée pour `app.flane` jusqu'à T5.4. Jamais silencieux. |
| Code livré sur le téléphone sans passer par le magasin : un compte EAS compromis, ou Claude depuis le PC, pourrait pousser du code à tout moment | Seule la variante de test reçoit des mises à jour ; **double authentification sur le compte Expo** (à confirmer par l'utilisateur avant la première publication : invérifiable depuis le dépôt ; et la session EAS ouverte sur le PC publie sans second facteur, d'où la règle « porte Observer seulement ») ; aucun jeton dans le dépôt ; `requireCommit` ; publication seulement à la porte Observer, du dernier commit de la PR, hash dans le message ; transport HTTPS ; **déclencheur** élargi sur constat de l'audit : signature par notre clé avant la première permission sensible, la première donnée personnelle stockée par `app.flane.dev` (`INTERNET` suffit à l'exfiltrer), ou le premier second appareil ou canal. |
| Une mise à jour casse l'appli au démarrage | `expo-updates` revient au code embarqué après un échec ; `fallbackToCacheTimeout: 0`. |
| Mise à jour appliquée sur une version native incompatible | Empreinte native : le serveur ne sert que les mises à jour de la même empreinte ; test « empreinte stable » ; `eas fingerprint:compare` après chaque build. |
| Fichier `.env` local avec des `EXPO_PUBLIC_*` embarqués par `eas update` | Aucun `.env` dans le projet ; `.gitignore` les couvre ; `requireCommit` ; le résumé de publication est relu. |
| Oubli du changement de version | Dans la définition de « fini » (modèle de fiche, `METHODE.md`) ; `package.json` seule source. |

Référence : `docs/SECURITE.md`, « Code et dépendances », « Entrées externes ».

- Cas limites : mode avion (critère 3) ; `updateStatus()` avec valeurs nulles, module désactivé, mise à jour reçue ; `updates.enabled` par variante ; empreinte stable entre variantes et versions.

## Prévoir sans construire

- `updates.enabled` par variante : la décision de T5.4 tient en une ligne.
- Canaux déjà nommés : un canal `beta` pour un testeur ami (jalon 5) s'ajoute sans code.

## Objections de l'avocat du diable

Seize objections le 2026-10-20. Réponses retenues :

1. **Empreinte changeant à chaque version** (bloquante) → vérifié : la version n'entre pas dans l'empreinte ; test « empreinte stable » ajouté.
2. **Empreinte différente entre build et publication** (bloquante) → vérifié : `development` et `preview` identiques ; publication toujours avec `APP_VARIANT=preview` ; `eas fingerprint:compare` après chaque build ; test de la configuration résolue.
3. **Critère 1 infaisable en une ouverture** (bloquante) → réécrit : deux fermetures complètes et réouvertures, pas de « moins d'une minute ».
4. **D-012 contredite en silence** (bloquante) → D-023, exception explicite, validée à Choisir.
5. **Critère 4 invérifiable** → réécrit : test de stabilité, garantie serveur, rien dans l'appli.
6. **Texte du produit changé pour le test** → retiré : la preuve est « Code embarqué » → « Mise à jour du … » dans « À propos », à la vraie porte Observer, sur le dernier commit.
7. **Code non audité publié, procédure floue** → `requireCommit`, publication seulement à Observer après audit, republication après correction, `update:republish` si refus.
8. **Compte compromis, parade insuffisante demain** → double authentification, déclencheur de signature écrit dans `SECURITE.md`, publication seulement à Observer.
9. **Publication sans interaction non spécifiée** → commande exacte dans la fiche et les conventions, canal sur le profil, essai à blanc avant le build.
10. **Schéma de version ambigu** → table d'exemples dans les conventions ; versionName de l'APK et version affichée expliqués (c'est le rôle de la version native).
11. **Dépendances incomplètes** → paquets tirés listés, liste réelle à la construction.
12. **Test « serveur injoignable » vide** → remplacé par valeurs nulles / module désactivé ; le réseau absent reste le critère 3.
13. **`development` avec mises à jour actives** → désactivées : seule `preview` reçoit.
14. **`METHODE.md` et modèle de fiche oubliés** → ajoutés au Dedans.
15. **Télémétrie d'`eas update`** → `EXPO_NO_TELEMETRY=1` dans la commande documentée.
16. **Budget serré** → les deux vérifications d'empreinte sont faites ; 1 session maintenue.
